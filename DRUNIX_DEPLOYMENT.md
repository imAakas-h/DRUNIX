# Deploy RASID chaincode on Drunix

## Scope and prerequisites

The commands below follow the official [NPCI Drunix test-network guide](https://github.com/npci/drunix/blob/main/drunix-network/test-network/README.md), not the generic Hyperledger Fabric sample network. They create a disposable local Drunix network for integration testing. Do not use its sample organizations, certificates, or endorsement policy as a production consortium configuration.

Complete [DRUNIX_SETUP.md](./DRUNIX_SETUP.md) first. This repository has not yet been deployed to Drunix. The current environment lacks WSL, Docker and Go, and no operator-issued network credentials/endpoints were provided.

## 1. Start the official NPCI test network

In Ubuntu:

```bash
mkdir -p "$HOME/src"
git clone https://github.com/npci/drunix.git "$HOME/src/drunix"
cd "$HOME/src/drunix/drunix-network/test-network"
./network.sh prereq
./network.sh up createChannel -c mychannel -s yugabyte
docker ps
```

`prereq` installs the network's required binaries and container images. The official sample defaults to `mychannel`, Go chaincode, cryptogen-generated material and Yugabyte. It has lite peers, committing peers, verification servers and a single-node Raft orderer. The exact deployed topology/configuration must be checked in the output and official repository before proceeding.

The upstream source currently requests Go 1.26.1 when building Drunix itself. Building from source is separate from running the sample's `network.sh prereq` flow. If you choose a source build, use the upstream build instructions and pinned commit; do not substitute Fabric binaries or a generic Fabric test network.

## 2. Deploy the existing RASID contract

From the official test-network directory, deploy the existing chaincode without replacing its business logic:

```bash
./network.sh deployCC \
  -ccn rasid \
  -ccp /mnt/d/Desktop/DRUNIX/chaincode/rasid \
  -ccl go \
  -ccv 1.0 \
  -ccs auto \
  -c mychannel \
  -ccep "AND('Org1MSP.peer','Org2MSP.peer')"
```

The sample MSP names and the two-organization policy above apply **only** to the official local sample network. For another Drunix deployment, the network operator must provide the channel, actual MSP IDs, approved endorsement policy, chaincode definition/version/sequence, and client-facing peer gateway endpoints.

The contract currently implements registration/duplicate rejection, buyer acceptance, discounting, ownership transfer/release, settlement, role checks and on-ledger audit events. The operator identity must be the first authorized caller to invoke `BootstrapOperator`; `npm run seed` then binds that Operator and registers the other six participants. Do not run first-time bootstrap on a shared network without the network owner's approval.

## 3. Configure and seed enrolled identities

Obtain distinct, network-issued credentials for the seven RASID identities from the Drunix/network administrator. For the sample CA mode, follow the enrollment procedures and credentials generated by the official Drunix scripts; the application does not enroll identities or fabricate certificates.

Use the *actual* peer gateway that serves Fabric Gateway requests and its TLS host name/root certificate. The official sample distinguishes lite-peer and committing-peer ports; use the gateway endpoint confirmed by that sample's current configuration. Do not copy old `7051`/`9051` values or guess endpoints. The Gateway peer routes orderer submission/status internally; this Node Gateway client does not open a direct orderer connection.

Follow [DRUNIX_CONFIGURATION.md](./DRUNIX_CONFIGURATION.md) to create the ignored local `identities.json`, set `.env`, protect credentials, and provide unique app-login passwords. The server will report `CONFIGURATION REQUIRED` until all seven identity entries and the active Operator credentials validate. It will never fall back to Development Mode.

From the RASID root:

```bash
npm run seed
npm start
```

`npm run seed` checks that bootstrap and each participant-registration transaction actually committed; it fails otherwise. The server starts in the `LEDGER_MODE` set by `.env` (the example selects `drunix`).

## 4. Check live status

Log in with the Operator's RASID application password. The dashboard status check evaluates `WhoAmI` using that Operator's configured certificate. `CONNECTED` requires a successful gateway query, identity authentication and chaincode execution; selecting Drunix does not mark the network connected.

The dashboard's last observed block is only populated from a successful `Commit.getStatus()` response. No block number, network name or endpoint is invented. A successful query proves read/connectivity, not that a transaction has been submitted; transaction-submission evidence comes from the actual integration tests or an accepted RASID business transaction.

To stop the local test network, from its test-network directory:

```bash
./network.sh down
```

Confirm the script's cleanup behavior in the checked-out Drunix version before running it if you need to preserve local test data.
